# Mainnet readiness audit -- 2026-09-26

Output of a read-only audit run at the owner's request ("start those steps to
implement what it needs to start using the app on mainnet"): six domain
auditors (wallet & funds safety, node lifecycle & data, install & supply chain,
security/privacy/network, ordinals behaviour on mainnet, verification &
rehearsal), one skeptic per domain re-checking every "done" claim, and a
completeness critic. The plan built from it is **PROGRESS.md, "Phase 10M --
Mainnet readiness"**; the ids below (`[domain/id]`) are what that plan refers to.

**Read this as a list of leads, not facts.** The auditors read code and
documents; nothing was built, run or executed by them. Several claims rest on
web summaries of third-party source (ord's CSP on `/preview`, rune-locking
behaviour, Core standardness rules) or on binary strings. CLAUDE.md's rule
applies: every item is *reproduced or disproved against the real binaries and
recorded in DECISIONS.md* before anything is built on it, and a claim that
turns out to be false is recorded as false. Line numbers cited here were
correct for the tree the auditors saw (about 30 lines off already, as the tree
kept moving).

Legend: `level` = blocker (do not use real funds on mainnet without it) /
should / nice; `status` = what the auditor claimed, `->` what the skeptic
corrected it to; `verifiable here` = can Claude verify it on the Windows dev
machine with regtest/signet/testnet4 and real binaries; `effort` S/M/L.


## Completeness critic

### Ordering advice (gates)

Treat this as gates. Each gate needs its evidence line (commit, exe hash, executed-versus-skipped test counts) before the next one opens. CLAUDE.md's one-task-at-a-time rhythm and the 2,600-line src-tauri/src/lib.rs mean Claude's coding work is serial. The real parallelism is between Claude's work and the owner's actions and wall-clock time (the sync).

G0 - Baseline, hardware, decisions (start immediately; the owner is the bottleneck).
- Owner: obtain or attach an NTFS SSD, free space on C: (measured 2 MB to 2.8 GB free while other work runs, so no release build is safe yet), and answer the decision batch D1-D10. D1, D3, D5 and D9 gate the code below.
- Claude: run the full gate on the current tree with live binaries and no skips, then commit Step 1(a) and tag RC0. Re-baseline every audit claim that cites line numbers or compile state, because the tree is moving. Add the Phase 10M section to PROGRESS.md and defer Steps 6-11.
- Nothing after G0 starts a build, a live test or a sync until there is disk for it.

G1 - Lifecycle hardening (must finish before any long sync starts; no wallet dependency).
Fix and test the restart failure loop, the orphan and adopt rules, warm-up-aware readiness and the stop and stderr items, on regtest first, then with a real release exe. This gate needs no owner decisions except D7. Build the release exe here for the first time (the process-handling work has only been proven with a probe and a debug exe). Do not add a generic executor timeout in this gate.

G2 - Bounded mainnet smoke (rung 2) with the release exe, owner present, before the multi-day sync.
Run mainnet for minutes: start, headers advancing, graceful stop, kill -9 then restart, stop then start over the same datadir, RAM and disk figures. Record what the stop and startup budgets really are. Then the owner starts the full IBD on the SSD (Stage A). This is the critical path: everything else is wall-clock parallel to it.
- Do not run heavy live tests while the IBD runs unless G2 measured the headroom. Pausing the node with a graceful stop is allowed.
- Do not start ord on mainnet until Core is out of IBD and txindex has caught up (the sequencing gap), and settle D5 first, because index options are effectively permanent per environment.

G3 - Wallet correctness on regtest and a public test chain (parallel with the IBD; needs G1, D1 and test coins).
In order: (1) Step 1(b) per D1, with encryption verified through getwalletinfo and mainnet failing closed. (2) The wallet state machine and identity record, atomic create and restore, seed-confirmed marker, and back-navigation in the seed view. (3) The in-flight registry with single-flight signing, and the ConfirmDialog reset fix. (4) The regtest delta tests: encrypted inscribe, batch and reinscribe; post-encryption receive address restored; descriptor counts; inscription equality; mainnet relay policy; unmined chaining. (5) The public-test-chain rehearsal in the release exe through the GUI with an ENCRYPTED wallet: create, confirm, fund from a faucet, send, restore into a second environment, small inscribe, a stuck-transaction observation. Test coins are an external dependency (faucets, waiting for sync), so start the sync early and use signet or testnet4 for the smaller size. Record every drill in the runbook. This gate depends on G1 because the rehearsal must run in the real release exe.

G4 - Hostile-content and integrity hardening (before ord's Explorer is first opened on mainnet, and before any wallet exists).
The Explorer renders mainnet inscriptions the moment ord catches up, with no wallet involved, so this gate is earlier than the wallet stages. Do D2 (opt-in or placeholders), the live IPC-isolation test in the real webview with a hostile HTML/SVG inscription, the set_setting key allowlist, re-verification of binaries at launch, and the owner's independent check of the key fingerprints and ord hashes (D3, owner-manual). Verify ord's CSP headers live (curl -I on /preview) instead of relying on the recorded rationale.

G5 - Independent review and canary scan (before Stage B).
Human review of the money path, the whole-IPC security self-review, and the canary harness (Step 3 first half) run over the event stream, SQLite file, debug.log, ord data directory, WebView2 profile and temp folder using a real mnemonic on a test chain.

G6 - Stage B, owner-run only (needs the sync and ord index complete, plus G3, G4 and G5).
The owner creates disposable wallet W-A in the GUI, writes the seed down, and receives one tiny amount. Backups: the public-descriptor backup exists first. Claude never sees the seed or passphrase.

G7 - Stage C then D.
Tiny self-send with the PSBT decode and second-source check; restore W-A's seed into a second environment (the drill on the real chain, where a full rescan takes hours; observe timeouts and progress); sweep to final wallet W-B; then a tiny inscription; then raise the cap in steps. Stop at any unexplained observation.

Runs in parallel: the drills and runbook writing, the decision-register work, pin verification by the owner, D4 (Tor or listen policy), the diagnostics harness. Must be serial: G0 before everything; G1 before the sync; the sync and ord index before mainnet wallet creation; G3 to G5 before G6; G6 before G7.

Where the owner must act: hardware, decisions D1-D10, the pin check, all seed and passphrase steps, real-P2P approval on test chains, the value cap, and the stop-or-continue call at every stage. Dropped from the critical path: MSI, signing, updater, remote mode, services, scheduling and update checker.

### Dangerous assumptions

- A PROGRESS.md checkbox or a DECISIONS.md summary proves a property. Counter-examples: Step 1(a) is ticked but its files were uncommitted (17 dirty paths when I checked); 'every automated test encrypts first' is false for the inscribe, batch and reinscribe live tests; 'projected usage' overstates the disk warning; some VERIFY records lack exact commands and output as CLAUDE.md requires.
- A green 'just check' means the real-binary tests ran. I confirmed the Justfile check recipe exports no NK_TEST_BITCOIND or NK_TEST_ORD, and the audits count about 19 early-return skip sites, so the gate can be green while the wallet, restore and inscribe tests did nothing. CI has been billing-blocked since 2026-09-24, so nothing from Phase 5 on has run there.
- The tree the audits described is the tree that will be built. It is moving: audits cite line numbers off by about 30 lines, disk free swung from about 2 MB to 2.8 GB while I worked, and one skeptic reported a compile error in private_keys.rs that the current file (slice-signature calls at lines 248 and 275) no longer shows. Nothing has been compiled or run in this read-only pass, so re-baseline before trusting either claim.
- Regtest behaviour is mainnet behaviour. Regtest has an empty chain, instant rescans, no fee estimates, a block mined after every action, all index options on, an unencrypted wallet in the inscribe tests, no rune outputs, no hostile content, no relay-policy rejection (no acceptnonstdtxn or standardness setting appears anywhere in the repo), and ord stops that took 4.6 s at height 0.
- Signet and testnet4 were rehearsed. They were only started, given a peer, seen with ord at height 0, and stopped. No wallet was created, funded or used on either (DECISIONS.md around 4123), and an unencrypted test-chain wallet cannot even sign today.
- Fixing Step 1(b) by 'skip the passphrase when the wallet is unencrypted' is enough. On signet or testnet4 that makes the rehearsal exercise the unencrypted path, not the mainnet unlock, sign and relock path. The rehearsal wallet must be encrypted.
- A debug build is a stand-in for the release exe. The release exe is a GUI-subsystem, panic=abort, stripped build with hidden child consoles, a different stdin situation, no application log, and a real WebView2 CSP. Only a probe stood in for it, and no release exe has ever been built.
- Mainnet wallet encryption is enforced. It is enforced in Rust only at create, is untested, is bypassable by a failed encrypt or an interrupted restore that leaves an unencrypted wallet, and mainnet 'fails closed' on such a wallet only because walletpassphrase errors. Console 'ord wallet send' on an unencrypted wallet needs no passphrase.
- 'Seed shown once and confirmed' means the user has the seed. No confirmed marker is stored, the confirm step cannot go back to the words, and after any interruption the encrypted, empty wallet still hands out receive addresses.
- Restore proves recoverability. Only total balance was compared on a tiny chain, using an address made before encryption. Inscriptions, the cardinal/ordinal split, post-encryption addresses and descriptor counts were never compared, and one audit's unverified evidence says ord's commit recovery key may live only in wallet.dat, not in the seed.
- ord's own coin selection protects inscriptions and runes. Nodekeeper has no such test and no protection code of its own. With the runes index off (the mainnet default) ord cannot see rune-bearing outputs, unsolicited inscriptions and runes are routine on mainnet, and the raw console can build and broadcast a spend from allowed RPC pieces.
- The dry-run preview equals what will be broadcast, and the mainnet confirmation is enforced. The real send is a fresh transaction not bound to the preview, the preview shows only the fee, and the backend enforces neither the preview nor the mainnet confirmation. The ConfirmDialog acknowledgement can also be left ticked after an error.
- Adding timeouts everywhere is a safe hardening. On signing and rescan commands a kill or timeout can strand a commit without its reveal or abort a restore. Several audits and PROGRESS.md Step 6 recommend timeouts without separating operation classes.
- 'Stopped' in the UI, a closed window or a finished Quit means bitcoind is not writing. A manual Stop untracks the node while it may still flush, the portable close path exits even if a stop failed, and a start timeout leaves an invisible bitcoind. The owner must be told to unplug only after a successful Safe Eject.
- The 60 s startup and 120 s bitcoind and 30 s ord stop budgets, and the dbcache sizing, hold on mainnet. They were chosen on empty chains. Even a CI run on an empty regtest chain hit StartupTimeout at 32 s and 62.8 s under load, and ord's own binary warns that recovery of a large index can take a long time.
- The pinned keys and hashes are trustworthy because the code fails closed. They came from one session over one channel, ord has no maintainer signature, expiry and revocation are not checked, at least four bundle keys are expired according to one audit, extracted binaries are never re-hashed, and the webview can repoint bitcoind_path and ord_path through set_setting.
- Findings taken from web summaries of third-party source are facts. Claims about ord's CSP on /preview, its rune-locking semantics, its recovery key and Core standardness came from summaries or binary strings, not runs against the pinned versions. Treat them as leads until a live command records the result.
- The machine can host mainnet. It has 5.9 GB RAM, a single volume, a default data root on that volume, and a disk that is close to full, and concurrent environments have never been run together live.

## wallet-funds-safety

The wallet plumbing is real and has been exercised against a real bitcoind 31.1 and ord 0.29.0 on regtest: create, encrypt-immediately, unlock/relock, dry-run send, real send, inscribe, batch, reinscribe and seed restore all have live tests, and the mnemonic never reaches the monitor stream. Almost every mainnet-specific safety property, however, lives only in React and has never run on mainnet or in a release exe. The backend does not enforce preview or the mainnet confirmation. A double click on Confirm can broadcast twice. The shared ConfirmDialog leaves its mainnet checkbox ticked after a failed attempt. The fee is not shown in the confirm step and there is no backend fee ceiling. A failed encryptwallet after ord wallet create leaves an unencrypted mainnet wallet and throws away the mnemonic. Encryption state is never checked at use. The GUI cannot send an inscription at all. Gallery previews run inscription JavaScript automatically, and the sandbox-versus-IPC criterion was never live-tested. Inscription and rune UTXO protection is delegated to ord and untested by Nodekeeper. There is no backup feature (Phase 10 step 4 is not started), no emergency runbook and no restore drill. Unencrypted test-chain wallets cannot sign at all (step 1(b)), so the natural signet/testnet4 rehearsal is blocked today. Treat the app as not ready for real funds until the blockers below are closed and a staged rehearsal has passed.

## install-distribution

The verification engine for the two third-party binaries is real and well tested. Bitcoin Core is checked against SHA256SUMS plus at least 3 distinct pinned-key signatures, and ord against pinned SHA-256 hashes. The owner has never independently checked the builder-key fingerprints or the ord hashes, the extracted binaries are trusted forever on path existence, and the generic `set_setting` IPC command lets the webview repoint `bitcoind_path`/`ord_path` at any executable. For the owner's own PC, the minimum is a release exe built from a clean tagged commit and run portably (a `config` folder next to the exe, data on a large NTFS drive), plus a runbook and the blockers below. An installer, code signing, a self-updater, bundled prerequisites and user documentation are only needed to hand the app to other people, and none of them exists yet.

## security-privacy-network

The core secret-handling machinery is real and mostly proven against real bitcoind/ord on regtest: executor redaction, the sensitive channel, position-based masking of console secrets, an extended-private-key backstop, in-memory-only passphrase remembering, and fail-closed binary verification. Mainnet has never been run and only a debug build has ever been launched, so the packaged webview boundary (CSP, capabilities, malicious-inscription-cannot-reach-IPC, scripts always enabled in inscription iframes contrary to Foundation D) is unproven, and the trust roots (39 builder keys, four ord hashes) were fetched by the agent and never independently checked by the owner. Two code-level blockers remain: the Step 1(a) console private-key fix is uncommitted (HEAD still records private descriptors), and mainnet wallet encryption is enforced only at creation with no fail-closed check afterwards (Step 1(b) not started). Beyond that, the IPC surface has no backend-enforced confirmation for any fund-moving command and includes arbitrary-code and arbitrary-file primitives (set_setting binary paths, inscribe_file_preview), the console can still build and broadcast a spend or unlock the wallet indefinitely, and installed binaries are never re-verified after install. Network privacy is unenforced (no allowlist mechanism, no Tor, bitcoin.conf is regenerated every start so the owner cannot configure a proxy), and there is no dependency auditing of any kind. This audit was read-only: nothing was built, run, or executed, so every done_verified below rests on recorded live results in DECISIONS.md and tests present in the tree.

## ordinals-mainnet-behaviour

The ordinals features in the spec (BTC send, single and batch inscribe, reinscribe, gallery, explorer, console, index gating) are built and were proven against real regtest bitcoind 31.1 and ord 0.29.0. Almost none of it has been exercised in the shape mainnet has: no real fee market, real mempool policy, a huge multi-day index, or spam inscriptions and runes arriving from third parties. I found three blockers by reading the code.
